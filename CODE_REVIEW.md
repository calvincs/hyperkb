P1 means fix in the next reliability release; P2 means a concrete correctness or performance issue to schedule next.

The multi-client problem is confirmed, but removing the process lock alone would expose existing races that can lose acknowledged writes. The first priority should be reliable storage and sync, followed by shared client access and retrieval correctness.

**High-priority findings**

1. **[P1] A new client kills an active server.** In [mcp_server.py:213](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/mcp_server.py#L213), identifying the lock holder as an MCP process is treated as proof that it is stale. There is no check for a disconnected client. The live protocol reproduction confirmed that opening B terminates A, which had just successfully listed tools. Automatic reconnects can repeatedly displace each other. Stop terminating healthy holders; implement a shared service or a design with coordinated access across processes. Preserve exclusive ownership until that coordination exists.

2. **[P1] A fresh installation can no longer import the MCP server.** Both optional dependency groups allow `mcp[cli]>=1.0` in [pyproject.toml:20](https://github.com/calvincs/hyperkb/blob/0dd61fe/pyproject.toml#L20), while [mcp_server.py:34](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/mcp_server.py#L34) imports `mcp.server.fastmcp`. The resolved MCP 2.2.0 explicitly rejects that import because the API changed. Bound both declarations to the supported major version as an immediate fix, or migrate and test against 2.x. Add a fresh-install/import smoke check so an existing development environment cannot hide this failure.

3. **[P1] Background sync can erase a write that returned success.** [sync.py:477](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/sync.py#L477) checks out a temporary branch and copies remote files directly over the live storage directory. `SyncEngine._lock` and `KnowledgeStore._write_lock` do not coordinate. In a controlled interleaving, sync checked out its temporary branch, `add_entry` successfully wrote and committed an entry, and sync then overwrote the file with its download. Sync returned `ok`; the acknowledged entry was absent from both disk and the index. Stage remote work separately and coordinate publication, Git changes, store writes, and reindexing through one mutation owner.

4. **[P1] Pull-only sync marks unuploaded changes as synchronized and can later discard them.** [sync.py:393](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/sync.py#L393) advances `last-sync` regardless of direction. Reproduction: synchronize a file, add a local entry, call `sync('pull')`, then call `sync('both')`. After the pull, Git reports no pending changes. The next sync pulls the old remote version onto the new baseline; the local entry disappears without ever reaching the remote. Track the last common state and pending uploads separately; a pull must not acknowledge an upload that never occurred.

5. **[P1] Push-only sync removes remote-only files from the published inventory.** [sync.py:546](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/sync.py#L546) replaces the entire remote manifest with the local directory inventory, although only `local_changes` were uploaded. Reproduction: another machine adds a remote file, this machine changes a different local file, and this machine calls `push`. The remote-only object still exists in S3, but its manifest entry disappears, making it undiscoverable through normal sync. Update the existing remote manifest only for successfully uploaded or explicitly deleted paths, using a snapshot read under the remote lease.

6. **[P1] The S3 advisory lock grants concurrent ownership.** [remote.py:232](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/remote.py#L232) performs an unconditional write after a separate read. Two machines that observe no lock can both return `True`; this was reproduced with two remote instances and a barrier between the reads and writes. The same-machine exemption also permits distinct processes to overlap, and release does not verify ownership. Use conditional acquisition, a unique operation/lease ID, renewal, and ownership-checked release. Read the manifest after acquiring the lease; the current sync flow reads it beforehand.

7. **[P1] In-place rewrites can destroy the source-of-truth file on interruption.** Updates use `Path.write_text` directly at [store.py:417](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L417); archive and compaction do the same. Opening for writing truncates the existing file. An injected mid-write failure left a 216-byte knowledge file as 16 bytes with no parseable entries. This is particularly relevant because [mcp_server.py:1840](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/mcp_server.py#L1840) handles termination with `os._exit`, bypassing cleanup. Write and flush a temporary file, then atomically replace the original. Archive operations also need recovery for partial completion across multiple files. Drain active mutations during shutdown.

8. **[P1] Entry updates accept delimiters that silently discard content.** [store.py:387](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L387) only checks that replacement content is nonempty. It omits the delimiter and size checks used by `add_entry`. Updating an entry to `replacement\n<<<\nTHIS PART WILL BE LOST` succeeds, but the parser retains only `replacement`; reindexing then removes the trailing text from the database too. Reuse a single content-validation path for creation and replacement before touching disk.

**Other confirmed findings**

9. **[P2] Reindexing loses concurrent index updates and exposes partial results.** Parsing occurs outside the write lock at [store.py:1883](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L1883). A write after parsing but before the rebuild is omitted from the new index; this was reproduced while the entry remained on disk. The rebuild also bypasses the database lock and uses the same connection as readers at [store.py:1899](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L1899). A concurrent reader observed zero entries during its uncommitted delete/reinsert transaction. Establish a consistent file snapshot and isolate the rebuilding connection or database. Coordinate the final publication with writes.

10. **[P2] Hybrid and ripgrep search ignore metadata filters.** The ripgrep branch only filters time and archive filenames before adding its results at [search.py:303](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/search.py#L303). `status`, `entry_type`, `author`, and `hostname` are applied only to BM25. A query requesting an active decision from one client/host returned a completed task from a different client/host in both `rg` and default `hybrid`; `bm25` correctly returned no result. Apply the same filters to all candidates before ranking and pagination.

11. **[P2] Deep context returns matching lines instead of complete entries.** Ripgrep results enter the merge first. When BM25 supplies the same entry, [search.py:503](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/search.py#L503) merges scores but retains the ripgrep line as `content`. `build_context(depth='deep')` consumes that partial content. A three-line entry containing a summary, a critical caveat, and recovery instructions returned only the summary. Keep snippets separate from canonical entry content; batch-fetch complete selected entries before packing context.

12. **[P2] Domain filtering happens after BM25's result limit.** [search.py:316](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/search.py#L316) discards other domains after the SQL query has already selected its global top results. With twelve higher-ranked matches in another namespace and one valid target match, `limit=10` returned nothing while `limit=20` found it. This also hurts default hybrid recall when BM25 stemming finds entries that literal ripgrep misses. Apply domain filtering in the SQL query before `LIMIT` and use consistent namespace matching across sources.

13. **[P2] Packed context exceeds its own token budget.** [store.py:1066](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L1066) adds all file-summary costs after packing entries against a fixed 200-token reserve. Twelve small entries with 200-character file descriptions produced `tokens_used=636` for a budget of 300, even using the implementation's own estimator. JSON structure and truncation notices consume additional space and are not counted. Budget the entire response incrementally, including summaries and metadata, and distinguish an estimate from a strict model-token guarantee.

14. **[P2] Archiving drops indexed provenance and leaves links at the old source.** [store.py:508](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L508) reinserts only status, type, and tags. A high-weight entry from `author-a` on `host-a` became normal-weight with empty author and hostname in SQLite, while its markdown still retained those values. Its outgoing link stayed indexed under the removed source entry. Compaction uses the same incomplete metadata transfer. Preserve all metadata and move/rebuild link rows in the same operation; provide a deliberate redirect policy for existing entry references.

15. **[P2] Remote deletions do not trigger reindexing.** [sync.py:511](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/sync.py#L511) removes deleted filenames from the `pulled` result, and reindexing only runs when `pulled` is nonempty. In a deletion-only sync, the file disappeared from disk, remained in SQLite, and sync returned empty change lists with `status='ok'`. Report deletions explicitly and reindex for every applied disk change, including deletion-only updates.

16. **[P2] A missing index prevents access to the tool that rebuilds it.** For an existing configuration, [mcp_server.py:432](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/mcp_server.py#L432) connects and immediately queries entries without initializing a missing schema. Removing only the index from a temporary KB produced `no such table: entries` during startup even though all markdown survived. The MCP reindex tool is unavailable because startup fails. Add startup recovery for a missing index and an offline admin rebuild command. Preserve a corrupt index for diagnosis rather than silently overwriting it.

17. **[P2] Slow tools block the MCP event loop.** Registered tools are synchronous, including the call to network/Git sync at [mcp_server.py:1642](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/mcp_server.py#L1642). The tested FastMCP 1.30.0 dispatcher calls synchronous functions directly on the event loop. In a controlled test, a 200 ms store operation delayed a callback scheduled for 20 ms until approximately 200 ms. Long ripgrep, reindex, Git, or network operations therefore delay other requests and cancellation. Offload blocking work through a bounded executor or worker queue, after fixing the storage synchronization described above. Move the synchronous startup update check off the initialization path as well.

18. **[P2] Ripgrep epoch recovery repeatedly rereads entire files.** [search.py:205](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/search.py#L205) loads and splits the complete file whenever before-context lacks an epoch marker. Consecutive matching lines repeatedly take this fallback. A 299,591-byte file with 300 matching lines in one entry caused 299 complete reads—89,577,709 bytes—to return one deduplicated entry, taking about 0.116 seconds on this machine. Cache an entry/line map per file for the request or retain the current epoch while processing the ripgrep stream. Bound work by unique entries rather than matching lines where possible.

**Original design discussion (superseded by the implementation choice below)**

My preferred starting point is **one shared service per knowledge base**, retaining markdown and SQLite. It would own writes, index updates, and one sync worker. Each client would have its own session context and provenance. Existing stdio client configurations could use a small adapter to that service. Direct connections from other machines would require an explicit transport and access model; that is a separate deployment decision.

Session isolation matters: anchors currently live in `AppContext`, and author identity comes from process configuration/environment. Simply exposing the current global store over a shared transport would not give clients independent anchors or reliable per-client attribution. Reconnection also needs idempotency keys so a retried write does not append a duplicate after its response was lost.

Additional product changes I would prioritize:

- **Add revision checks, undo, and backup/restore.** A stable entry ID plus separate creation/update timestamps would make concurrent edits and durable references easier to manage than incrementing timestamps on collisions. Expected-revision checks can prevent one client from unknowingly overwriting another's update.
- **Add an offline repair path.** Provide admin commands for health, rebuild, and restore so MCP startup failure cannot lock users out of recovery. Health checks should compare content/revisions as well as counts; equal counts do not prove that file content and the index agree.
- **Clarify compaction's purpose before expanding it.** [store.py:677](https://github.com/calvincs/hyperkb/blob/0dd61fe/hyperkb/store.py#L677) concatenates prose and archives originals; it does not summarize or reduce that prose, and summaries become `note` entries. Decide whether this feature is grouping or actual summarization, and protect task/decision semantics. The documentation's append-only claim also needs to match the supported in-place update behavior.
- **Make MCP inputs and outputs more predictable.** Use validated action/mode enums, consistent structured results, explicit errors for unsupported values, and pagination for large file/task listings. Advertised exact/regex search should have explicit semantics: current multiword ripgrep searches use OR matching, and the public tool does not expose the low-level regex flag. Replace stale suggestions for removed commands such as `hkb add`, `hkb create`, and `hkb list` with the current MCP operations.
- **Measure realistic mixed workloads.** Add tests with multiple live clients, interleaved sync/writes, interrupted writes, push/pull sequences, and restart recovery. Track search latency, event-loop delay, write latency, and index freshness at representative KB sizes. Existing unit coverage is substantial, but the default green suite did not detect the reproductions above.

I would sequence the work as: dependency compatibility and data preservation first; shared service/session support next; then retrieval correctness and measured performance improvements. The most useful near-term improvements are reliable writes, trustworthy retrieval, and clear recovery behavior.


## Implementation status — September 11, 2026

The reliability work addresses findings 1–18. The selected multi-client design keeps one stdio process per client with a shared storage mutation lock, independent session context, and one elected background sync worker per local KB. This preserves existing client configuration; no shared HTTP daemon was introduced.

Additional fixes include literal handling of option-like ripgrep queries, current tool names in health repair hints, validated atomic config writes, environment credential precedence, read-only offline diagnostics, corrupt-index quarantine, task pagination, and explicit batch truncation. Sync adds manifest version 2, immutable blobs, deletion tombstones, and ETag publication checks. **All clients sharing a remote destination must upgrade before publication.**

Root validation passed **875 tests in 47.98 seconds** using `python -m pytest -q`. Independent live-protocol acceptance ran three clients, 60 acknowledged writes, six interleaved reindexes, and a restart; all entries and source labels survived. A 600-token estimated context budget produced a 588-token estimate with complete selected entries. A synthetic 296,620-byte file with 300 matching lines required one full-file epoch-map read and returned one entry in 0.013 seconds; this is not a production capacity estimate. The suite also covers interrupted writes and sync, lease takeover, and a clean temporary installation with all extras. The fresh install selected MCP 1.30.0 and passed dependency/import checks from its installed wheel in isolation. Both sync dependency groups now require `boto3>=1.40.0`; official SDK wheel models confirm the required conditional operations at that conservative floor and their absence in 1.34.0. S3 was exercised through Moto; no production bucket was accessed. Windows lock support was implemented but not run on Windows.

The website now uses canonical Markdown to generate human guides and machine-readable references, following Agent Mesh's documentation pattern. Static output is explicitly allowlisted and validated for source parity, human and Markdown links, fragments, and sitemap coverage: 15 HTML pages and 39 total public files. Desktop and 300-pixel effective narrow layouts were inspected; walkthrough/manual pause, mobile navigation, guide filtering, and code-copy behavior were exercised in the browser. The landing page includes an illustrative Record → Keep → Recall animation, pause/manual controls, and reduced-motion styling. Publication remains a release step.

## Remaining discussion items

- Add durable idempotency receipts and optimistic revision checks before claiming safe blind retries or conflict-free concurrent edits. Atomic publication prevents partial writes; it does not prevent a later intentional update from replacing an earlier one.
- Measure realistic mixed workloads. Indexed reads remain available while sync holds its mutation lock, but writes can wait through network operations. Moving download work outside the lock requires snapshot/revision validation before publication.
- Define retention and garbage collection for immutable remote blobs, tombstones, baselines, and Git history. This update favors recoverability and retains history.
- Stream or bound large ripgrep responses without truncating filtered recall. The epoch-map cache removes repeated file reads, but output and result candidates still occupy memory.
- Consider explicit backup/restore and entry history/undo commands. Offline diagnostics and reindexing are now available; they are not a complete backup system.
